## 嵌入式项目：开发目录与发布目录强制分离

用户要求：所有嵌入式开发项目及后续新项目均遵循本流程。此规则是持续工作约定，不代表自动获得提交、推送、建仓或烧录授权；继续遵循当前会话已明确授权的范围。

1. **先确认目录身份**：每次任务核对开发目录、发布目录、Git 根目录、分支、remote 和工作区状态。开发目录保存真实 Wi-Fi/API Key/token/密码、设备标识、私有证书配置及实机产物；后续 Git 提交、推送、PR 和源码发布统一在独立发布目录操作，禁止误推开发目录继承的旧 remote/历史。
2. **记录并复用映射**：以本文件的项目映射为准并实时核实。未建立映射时，默认候选为开发目录同级的 `<项目名>-release`，发布前检查是否存在、是否属于同一项目及 remote 是否正确，再建立并写明映射。候选路径不是已验证的仓库。处于发布目录时复用当前目录，不得创建 `-release-release`。多个副本/子工程先确认归属，不能混推。
3. **最小同步**：从开发目录按明确文件清单同步源码、构建定义、依赖锁文件、许可证、匿名测试和文档/配置模板。保留已有改动；不得整目录盲拷、复制 `.git`、盲目 `git add .` 或用带删除选项的同步覆盖发布目录。删除和重命名必须单独核对差异，不留过时源码，也不删除无关工作。
4. **私密信息留在本地**：识别项目实际使用的本地配置，并在开发与发布目录维护对应 `.gitignore`；只提交无真实值的 `.example.*` 模板。API Key、密码、token、私钥、私有证书配置、真实接口响应、设备清单、个人网络信息不得进入源码、文档、截图或日志输出。`.gitignore` 不会自动移除已跟踪文件和历史中的秘密。
5. **不发布个人构建产物**：固件可能嵌入凭据；默认排除 `.bin`、`.elf`、Flash/NVS dump、构建目录、缓存、串口日志、工具会话与备份。若用户明确要求发布二进制，必须从无个人凭据的发布配置重新构建并检查产物；不能直接上传实机使用的固件。
6. **发布前双重检查**：检查待提交文件清单、实际暂存差异和将推送的全部历史；使用 Gitleaks 或等效秘密扫描，并在本地与已知凭据做无回显匹配。扫描报告必须脱敏，不得打印密钥。发现泄露时先停止相关发布；已外泄的凭据需撤销/更换，不能靠删除最新文件掩盖历史。凭据撤销仍按当前授权范围执行。
7. **历史规则**：首次创建全新、独立发布仓库时，可使用经过审查的干净初始提交，不继承未经审计的开发目录历史；已经存在的发布仓库必须保留连续历史。不得每次重新初始化、覆盖 remote、强推或擅自改写已发布历史。
8. **验证可复现配置**：在发布目录使用模板/占位配置检查构建及必要测试，确认构建不依赖未发布的私密文件。README 写清开发板、工具链、配置复制、凭据获取、站点/设备 ID（如适用）、TLS、构建/烧录/串口步骤及故障排查，不填入用户真实值。构建通过不等于实机、屏幕或电气验收通过。
9. **提交与远端回读**：获得相应授权且检查通过后，仅在已验证的发布目录暂存明确文件、提交与推送；再核对远端可见性、分支、提交及文件。新仓库未指定可见性时默认私有。结果报告标明仓库链接、发布目录、验证结果与尚未验收项。
10. **新项目与协作**：新建、复制、迁移嵌入式项目时，将本规则和目录映射带入项目 `AGENTS.md`；交给 DSH/其他代理时传递同一约束，只提供任务所需源码，不传递凭据。记忆和映射只是定位线索，每次发布都要核实实际目录和远端。
